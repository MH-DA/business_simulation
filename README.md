# 사장님 AI 마케팅 도우미

BA AI 경영 시뮬레이션 팀 프로젝트. 사장님이 네이버 플레이스 링크를 입력하면 공개 데이터를 근거로 가게 상태를 진단하고, 챗봇 상담으로 지금 필요한 마케팅 실행 방법을 함께 찾아주는 웹 서비스.

- 기획서: [PROJECT.md](PROJECT.md)
- 개발 워크플로우(스택, 화면↔데이터, 단계별 진행): [WORKFLOW.md](WORKFLOW.md)

## 핵심 원칙

- 점수화하지 않는다. 종합 점수·가중치·순위 없이 사실(수치)만 보여준다.
- 숫자는 경쟁사 비교 모듈이 계산한 것만 쓰고, LLM은 지식베이스를 근거로 설명과 문구화만 한다.
- 무엇을 먼저 할지는 서비스가 정하지 않고, 근거를 보여준 뒤 사장님이 판단하도록 돕는다.
- 처음에는 Mock 데이터로 만들고, 실제 수집기는 마지막에 붙인다.

## 경쟁사 분석 흐름

경쟁 매장을 사장님이 고르지 않는다. 가게의 지역과 업종으로 추적 키워드를 하나 정하고, 그 키워드로 검색했을 때 1위로 노출되는 가게를 비교 대상(경쟁 매장)으로 본다. 비교는 우리 가게와 1위 가게 두 곳뿐이다.

1. 수집기가 가게의 지역과 업종을 읽는다.
2. 거기서 추적 키워드를 하나 정한다. (예: "노원 헬스장")
3. 그 키워드로 검색해서 순위 목록을 가져온다.
4. 우리 가게와 검색 1위 가게의 비교 항목 9개를 수집한다.
5. 웹이 우리 가게의 순위와, 우리 가게 vs 1위 가게의 비교 항목 표를 보여준다.

비교 항목 9개 (우리 가게와 1위 가게의 값을 나란히 보여주고, 점수·높음/낮음 판정은 하지 않는다):

| 항목 | 값 | 비교 방식 |
|---|---|---|
| 별점 | 숫자 | 우리 가게와 1위 가게의 값, 차이 |
| 방문자 리뷰 수 | 숫자 | 〃 |
| 블로그 리뷰 수 | 숫자 | 〃 |
| 소개글 | 있음/없음 | 두 가게 각각 있는지 |
| 편의시설 | 있음/없음 | 〃 |
| 쿠폰 | 있음/없음 | 〃 |
| 예약 탭 | 있음/없음 | 〃 |
| 네이버페이 | 있음/없음 | 〃 |
| 최근 새소식 일자 | 날짜 | 수집 시점 기준 며칠 전인지 |

정해 둔 규칙:

- 추적 키워드는 "지역 + 업종" 규칙으로 만들고, 한 번 정하면 저장해서 바꾸지 않는다. 그래야 같은 가게의 순위 변화를 시점별로 비교할 수 있다.
- 순위는 수집 시점의 순위다. `collected_at`과 함께 저장하고 화면에도 수집 시점을 표시한다.
- 새소식 일자는 "오늘"이 아니라 수집 시점(`collected_at`)을 기준으로 경과일을 계산한다. 같은 데이터는 언제 열어도 같은 값이 나온다.
- 비교 대상은 검색 1위 가게 한 곳이라 평균은 계산하지 않는다. 한 곳의 값이므로 1위 가게가 어떤 곳인지(가게 이름, 키워드, 수집 시점)를 표와 함께 보여준다.
- 우리 가게가 순위권 밖이면 "순위권 밖"으로 표시하고 비교는 그대로 진행한다. 우리 가게가 1위이면 2위 가게와 비교한다.
- 4단계는 "지표 계산"이 아니라 "경쟁사 비교 모듈"이다. 우리 가게와 1위 가게의 9개 항목을 같은 형태로 맞추고, 차이값과 경과일만 계산해서 화면과 챗봇에 넘긴다.
- `Finding`(신호 유형) 목록은 만들지 않는다. 높음/낮음 같은 판정 없이, 챗봇이 근거로 쓸 사실(수치, 있음/없음, 날짜)만 남긴다.
- 기존 키워드 비율, 경쟁 평균 대비 %p 차이, 마케팅/비마케팅 분류는 코드에 남아 있지만 경쟁사 분석 화면에는 쓰지 않는다. 위 비교 항목 기준으로 `lib/metrics`를 개편할 예정이다.
- 검색 결과 수집 방식은 약관과 차단 가능성을 수집기 담당이 먼저 확인한다. 이것이 6단계의 가장 큰 불확실성이다.

## 폴더

```
app/          화면(/ , /guide, /analyzing/[jobId], /result/[placeId])과 API route
components/   StoreCard, KeywordChip, InsightCard, EvidenceCard, ConfirmCard, ChatPanel ...
lib/
  providers/  데이터 공급자 (PlaceDataProvider 인터페이스, MockProvider)
  metrics/    경쟁사 비교 (점수화 없음, 4단계)
  knowledge/  지식 조각 검색 (신호 묶음 가중치, 5단계)
  llm/        질문 분류, 프롬프트, Claude 호출, 근거 검증 (5단계)
data/
  places/     매장별 수집 결과 JSON (현재는 가짜 샘플)
  knowledge/  RAG가 읽는 지식 조각 (principles.json, guardrails.json)
types/        공통 데이터 타입
docs/
  design/     Figma 화면 이미지
  knowledge/  지식 원본 HTML (사람이 읽는 원본)
```

## 실행 방법

```bash
npm install
cp .env.example .env.local   # 필요한 키만 채운다 (Mock 개발은 비워도 됨)
npm run dev                  # http://localhost:3000
npm run typecheck            # 타입 검사 (라우트 타입을 먼저 생성한다)
npm run lint
node --test lib/place-url.test.ts lib/metrics/metrics.test.ts lib/llm/llm.test.ts   # 단위 테스트
npm run build
```

shadcn/ui 컴포넌트는 `components.json` 설정이 되어 있어서 필요할 때 추가한다: `npx shadcn@latest add button card input badge`

## 챗봇 동작 (5단계)

1. 질문을 규칙(키워드)으로 분류한다: 의도(신규 유입 / 재방문 / 강점 홍보 / 불편 개선)와 유형(진단 설명 / 실행안 생성 / 판단 보조). 빗나가는 자유 질문이 많아지면 LLM 분류로 바꾼다.
2. 우리 가게와 1위 가게의 비교 사실 9개를 표로 만든다. 수집 전인 값(네이버페이, 새소식 날짜 등)은 "수집 전"으로 표시하고 LLM에게도 모른다고 알린다.
3. 지식 조각을 고른다. `signalTypes`에 걸리는 신호를 묶음별 가중치(질문 의도 3 > 질문 속 주제어 2 > 비교 사실 1)로 세어 최대 3개를 뽑는다. 노출 지식(`exposure.json`)은 쓰지 않는다.
4. 지식 조각, 비교 사실, 가드레일 전부, 공통 규칙(점수·순위 금지, 없는 숫자 금지, 혼재 단정 금지)을 묶어 Claude에 보낸다.
5. LLM은 답변과 함께 쓴 지식 ID를 `[[근거: ...]]`로 내보내고, 서버는 검색 결과에 있는 ID만 근거 카드로 보여준다. 판단 보조형은 `[[확인: ...]]` 확인 카드로 끝난다. 표시 줄은 화면에 노출되지 않게 걸러낸다.

모델은 `LLM_MODEL`(기본 `claude-sonnet-5-5`)로 바꾸고, 호출은 `lib/llm/anthropic.ts` 한 곳에서만 한다. 확인 카드의 버튼 선택은 아직 저장하지 않는다(`/api/answers`는 이후 단계).

## 참고

- 업종은 `types/index.ts`의 `INDUSTRIES`에 정의한다: 음식점, 카페, 공방, 헬스장, 스터디카페. PROJECT.md의 대상 업종에는 공방이 아직 없으니 맞춰서 갱신할 것.
- 환경변수는 `.env.example`을 복사해 `.env.local`로 만든다. API 키는 서버에서만 사용한다.
- `data/places/`의 샘플은 가짜 데이터다. 실제 매장 정보가 아니다.
